# SAT-SA Phase 2 — Identity and actor/approver authentication foundation

Status: **IMPLEMENTED** (credential-based authentication for `POST /identity` and the new credential-issuance route) / **NOT IMPLEMENTED, DOCUMENTED AS AN OPEN GAP** (the legacy MLOps dashboard's `actor`/`approver` fields on `/registry/approve`, `/registry/revoke`, `/registry/trust`, `/deployment/*`).

## D1 — Tracing the actor/approver flow (current repository, re-verified)

Phase 1 flagged unauthenticated `actor`/`approver` fields generically. Re-tracing it directly in Phase 2 (Rule 2: verify, don't trust the prior write-up) found two genuinely distinct instances of the same underlying problem, with different blast radii and different fixes:

**Instance 1 — `qsmlops/api/app.py` (the legacy MLOps dashboard).** `ApproveRequest.approver`, `RevokeRequest.actor`, `TrustRefreshRequest.actor`, `DeploymentRequestBody.actor`, `RollbackBody.actor` are Pydantic fields with defaults like `"api"`/`"operator"` — free text, never checked against any identity. Traced downstream: these strings flow into `pipeline.registry.revoke(version_id, actor, reason)`, `pipeline.request_approval(version_id, approver)`, etc., and ultimately into ledger/audit records as the recorded actor — meaning the audit trail can currently record any string a caller supplies as having approved or revoked a model version.

**Instance 2 — `qsmlops/api/foundation.py` (the Phase 1/2-owned foundation layer).** Found fresh during this phase's own re-verification, not carried over from Phase 1's write-up: `POST /identity` accepted a `CreateIdentityRequest` with a `role` field validated only for *existing in the role vocabulary* — **any caller could request `role: "admin"`** (or any other built-in role) and receive a fully privileged identity record, with zero authentication of the caller. This is more severe than Instance 1: it does not merely mis-attribute an action to a false name, it lets an unauthenticated caller mint a genuinely privileged principal.

## D2 — What identity guarantees actually exist

None, at the HTTP boundary, before this phase. `qsmlops/security/identity/` and `qsmlops/security/permissions/` are real, well-structured modules (`Identity` records with roles/permissions, a `domain.action` permission vocabulary, `has_permission`/`require_permission`) — but nothing bound an inbound HTTP request to one of those records. No session, no API key, no signature check, no SSO of any kind existed anywhere in this repository (confirmed absent, not merely unfound). Per Part D2's explicit instruction, this document does not claim otherwise, and Phase 2 did not invent enterprise SSO — it built the smallest real mechanism that lets a caller be resolved to an actual `Identity`: a local API-key credential.

## D3/D4 — What was built

**Credential model** (`qsmlops/security/identity/auth.py`, new module): a credential is `f"{key_id}.{secret}"` — `key_id` is a non-secret random lookup prefix (16 hex chars), `secret` is a 32-byte URL-safe random token. Only a per-credential-salted SHA3-256 hash of `secret` is ever persisted (new `identity_credentials` table, migration version 3 in `qsmlops/database/migrations.py`); the raw secret is shown to the caller exactly once, at issuance, and cannot be recovered — only reissued (rotation invalidates the previous credential immediately, verified by test). Comparison is constant-time (`hmac.compare_digest`).

**`IdentityService`** gained `issue_credential(identity_id) -> str`, `revoke_credential(identity_id)`, and `authenticate(raw_token) -> AuthenticatedPrincipal`. `authenticate()` deliberately raises the same `AuthenticationError` for "no such key_id," "hash mismatch," "revoked credential," and "inactive identity" — distinguishing these would let an attacker enumerate valid `key_id`s by timing/response differences.

**`POST /identity`** (`qsmlops/api/foundation.py`): the very first identity on a fresh installation (identity list is empty) is a documented **bootstrap exception** — created without a credential, because there is nothing yet to authenticate against — and its response includes a freshly issued credential. Every identity created after that requires a resolved `AuthenticatedPrincipal`; a principal without `identity.manage` may only create an identity that lists itself as `owner` (self-service), not an arbitrary owner. A new `POST /identity/{id}/credential` route lets a principal with `identity.manage` (or the identity itself) mint/rotate a credential for an existing identity — without this, only the single bootstrap identity could ever authenticate, which would make the whole mechanism useless beyond the first call.

This directly maps to Part D4's authority tiers using the **existing** role vocabulary (no new roles invented): `admin` (has `identity.manage`, full authority), the pre-existing human roles (`ml_engineer`, `security_analyst`, `operator` — self-service only under this new rule), pre-existing service roles, and pre-existing agent roles (`AGENT_OBSERVE`/`AGENT_RECOMMEND` only, never `identity.manage` — unchanged, already least-privilege before this phase).

## D5 — Tests

`tests/test_phase2_identity_auth.py` (14 tests): credential generation/verification/tamper-rejection at the mechanism level; `authenticate()` against unknown key_id, revoked credential, rotated-away old credential, and deactivated identity, all at the service level; and the full API-level scenario set Part D5 names explicitly — missing identity (no header, post-bootstrap → 401), invalid identity (garbage token → 401), unauthorized action / ownership mismatch (non-privileged principal creating an identity owned by someone else → 403), and valid authorized action (self-owned creation → 201). `tests/test_foundation.py::test_identity_endpoint_lifecycle` was updated (not deleted) to authenticate as the bootstrap admin identity for its sequence of calls, since it exercises `IdentityService`'s duplicate/kind/role validation rather than authentication itself — documented inline in the test with the reason for the change, per Part O.

## What was deliberately NOT done, and why

**The legacy dashboard's `actor`/`approver` fields (Instance 1) were not retrofitted with authentication in Phase 2.** Traced concretely before deciding this: `qsmlops/api/app.py::create_app(pipeline)` builds a standalone FastAPI app from a bare `SelfHealingMLOps` pipeline with **no identity service at all** — confirmed by reading `test_phase5_registry_api.py`'s test fixture, which constructs the dashboard app this way. Wiring real authentication into these routes would mean changing `register_dashboard_routes`'s signature to require an identity service everywhere it's called (both the container-wired `qsmlops.app.build_app` and the standalone `create_app`), which is exactly the kind of larger, more invasive change to a system Phase 1's own [target-architecture.md](../phase1/target-architecture.md) explicitly recommended preserving as a separate, legacy bounded context rather than retrofitting — SAT-SA's own future API is specified to require authentication on every mutating route from day one instead (see [requirements-traceability.md](../phase1/requirements-traceability.md) SAT-HUM-01, GAP-07). This is a disclosed, deliberate scope boundary, not a hidden one: it is called out again in the Part R security review below and in the Phase 2 final report.

**Read routes (`GET /identity`, `GET /audit`) remain unauthenticated.** These expose identity metadata (name, role, permission list) and audit event summaries, not secrets. Protecting every read route was judged to be a larger change (would also require updating several existing read-only test calls) for a comparatively low-severity information-disclosure risk, and is out of Part D's explicit scope (which is about actor/approver *mutation* claims). Tracked as an open item for a later phase, not silently dropped.

## Unresolved security issues (carried into Part R)

1. Legacy dashboard `actor`/`approver` fields remain unauthenticated (Instance 1, above) — the audit trail for model approval/revocation/deployment can still record an unverified claimed actor.
2. `GET /identity` and `GET /audit` remain open to any caller with network access to the API.
3. The bootstrap exception is a real, if narrow, window: on a freshly initialized installation, whoever makes the first `POST /identity` call becomes the initial credentialed principal. This is a common pattern (first-run admin bootstrap), but it means the very first API call after installation is security-relevant and should be made by the operator immediately, not left open on a network-reachable instance.
