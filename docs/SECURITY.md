# SAT-SA security and deployment boundary

Phase 20 security review of the hosted system (threat model, authorization
matrix, secrets and logging, failure model, and the tests and CI checks that
back them): [`docs/security/`](security/THREAT_MODEL.md).

## Application controls

The `/api/v1` surface authenticates existing QSMLOps credentials and persistent
sessions. Session rows have expiry/revocation state; browser cookie mutations
require the session-bound CSRF token. Bearer credential requests are supported
for API clients. Membership roles and permissions are evaluated server-side,
and tenant repositories include organization ownership in resource access.
Opaque IDs do not authorize access. Upload, run, decision, receipt, verification,
and audit operations retain these checks below HTTP routing.

Production settings fail closed unless an explicit PostgreSQL URL, S3 backend,
TLS object endpoint, pre-existing TRUST-SAT key, durable ledger path, secure
cookie mode, explicit host list, HTTPS origins, and disabled runtime migration
are configured. `SATSA_S3_ACCESS_KEY` and `SATSA_S3_SECRET_KEY` must be supplied
together or both omitted for provider workload identity. Secrets belong in the
deployment secret manager or mounted secret files, never source control.

The local Compose stack uses development mode, loopback API binding and
single-node object storage. It is an integration environment, not a secure
hosted deployment. Production needs TLS at a trusted reverse proxy, exact
`SATSA_ALLOWED_HOSTS`, exact HTTPS `SATSA_ALLOWED_ORIGINS`, secure cookies,
explicit trusted proxy addresses when forwarded headers are enabled, private
object storage, network policy restricting PostgreSQL/object endpoints, and
operator-managed backups. Do not use wildcard CORS with credentialed requests.

S3 object keys are generated by the service from tenant/version scope and
server-calculated SHA3-256 content digests. Clients cannot choose object keys.
The bucket must remain private with public access/listing disabled. The API
checks tenant ownership before any object operation; bucket ACL/policy is not
the tenant boundary. Upload bytes pass through a bounded temporary file and are
streamed to object storage. The database records `uploading`, `stored`, or
`failed` state so retries can recover an interrupted write. Storage-side
versioning, retention, encryption, and lifecycle deletion remain provider
configuration responsibilities. Never expose provider credentials or build
public artifact URLs into API responses.

## Network and process controls

`/health/live` only reports process liveness. `/health/ready` checks database,
migration, signing-key configuration and storage reachability. The worker
readiness command also checks the queue table. API and worker are separate
services. Worker shutdown stops new claims and lets current work reach an
existing safe boundary; forced termination relies on persisted checkpoints and
lease expiry/recovery. PostgreSQL pool sizes and query timeouts are bounded by
settings. Request bytes and API rates are bounded independently.

The API and analysis worker use the repository's structured logging formatter
in production. HTTP response records include the generated request ID, route
template, method, response status, duration, and available user/organization
context. Worker events include run/execution/worker/stage fields where emitted.
Request bodies, bearer values, cookies, artifact bytes, and signing secrets are
not logged by the middleware. Operators should still restrict log access and
retention because tenant/resource identifiers and error diagnostics are
operationally sensitive.

Do not trust forwarded client IP or scheme headers unless the peer is an
explicitly configured trusted proxy. The API is intended to sit behind a TLS
terminator in hosted deployments. Avoid exposing PostgreSQL, object storage,
or internal worker ports to the public network.

## TRUST-SAT key and proof boundaries

Production does not create signing keys at API/worker startup. Provision the
ML-DSA-65 key into the protected `SATSA_TRUST_KEY_DIR` before starting services.
The private key is not stored in PostgreSQL or returned through the API. The
key file must be backed up and access-restricted by the deployment environment.
Key rotation is not managed by a KMS/HSM integration in this phase; coordinate
key replacement and public verification material operationally. An invalid or
missing key prevents production startup/finalization.

TRUST-SAT signs the documented canonical SHA3-256 representation and binds the
persisted supervisory decision. The append-only file ledger commits the trust
event, and a PostgreSQL advisory lock serializes ledger appenders across the
API/worker processes when they share that file. Therefore all instances must
mount the same durable ledger path. This arrangement assumes a shared filesystem
with reliable append/fsync semantics; it is not equivalent to a managed external
trust anchor and requires deployment-specific validation before multi-host use.

Verification proves integrity/authenticity of the recorded canonical state
against the receipt's public key and ledger chain. It does not establish that
real-world submitted evidence was truthful, that an operator-controlled
database/filesystem/key was never jointly replaced, or that the service is
absolutely tamper-proof. Artifact bytes are separately checked against their
server-recorded digest during validation; the current TRUST-SAT receipt verifier
does not fetch each physical S3 object during every receipt verification.

Evaluated behaviour (EXP-T01, one controlled synthetic workflow, see
[EXPERIMENTS.md](EXPERIMENTS.md)): the verifier rejected each of 13 tested
single-field mutations of canonical state — decision action and reason,
finding, risk, recommendation, observation scope, source provenance,
submission record payload, artifact digest, canonical payload, receipt
signature, receipt public key and ledger chain — and still verified after a
change to an unsigned operational queue field. This is "detected all tested
mutations", not a detection rate: coordinated replacement of database, key
and ledger together was not tested. Measured cost on one machine (EXP-O01):
finalization median 0.288 s, verification median 0.062 s.

## Reporting and response

Errors returned to clients use the documented bounded error envelope and do
not contain SQL, stack traces, credentials, or filesystem paths. Logs must not
include password/session/bearer tokens, signing material, uploaded contents, or
full evidence payloads. Dependency scanning, secret scanning, external
penetration testing, incident response, key escrow, and managed disaster
recovery are operational tasks not claimed as completed by this repository.
